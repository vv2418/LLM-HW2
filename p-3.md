### Why Use Docker Stack Deploy vs Docker Compose?

| Feature | `docker compose up` | `docker stack deploy` |
|---------|-------------------|---------------------|
| **Orchestration** | Single host | Multi-node cluster |
| **Scaling** | Manual | Declarative with auto-balancing |
| **High Availability** | No automatic recovery | Automatic failover across nodes |
| **Load Balancing** | External required | Built-in ingress load balancer |
| **Rolling Updates** | Container recreation | Zero-downtime updates |
| **Secrets Management** | Environment files | Encrypted secrets API |
| **Service Discovery** | Docker DNS (single host) | Swarm overlay network |

**When to use Stack Deploy:**
- Production multi-node deployments
- High availability requirements
- Automatic service recovery needed
- Horizontal scaling across hosts

**When to use Compose:**
- Development environments
- Single-server deployments
- Testing and prototyping
- When using Compose V2 features not in Swarm

## Deployment

### Known Limitation: Swarm Incompatibility

The Dify `docker-compose.yaml` file uses extended `depends_on` syntax:

```yaml
depends_on:
  db:
    condition: service_healthy
  redis:
    condition: service_healthy
```

**This is NOT supported in Docker Swarm** (Compose v3.x format).

**Error when attempting:**
```bash
$ docker stack deploy -c docker-compose.yaml dify
services.worker.depends_on must be a list
```

**Solution:** Use Docker Compose for deployment (as recommended by official Dify documentation here - https://docs.dify.ai/en/getting-started/install-self-hosted/docker-compose ).

### Deploy with Docker Compose

```bash
# Ensure you're in the docker directory
cd ~/path/to/dify/docker

# Start all services
docker compose up -d
```

**Expected Output:**
